# 数据库设计

## 1. 总体架构

平台采用多存储组合方案:

- MySQL: 平台业务状态
- Neo4j: 知识图谱实体与关系
- Milvus: 文档向量索引
- 本地文件系统: 上传原始文档与 JSON 回退状态

当前实现中:

- MySQL 是账号、会话、聊天历史、评测状态、文档状态的主持久化
- 后端会把同一份状态同步到本地 JSON 文件，便于离线运行和故障回退
- 文档原文件不存入 MySQL，而是存储在后端文件目录

## 2. MySQL 设计

### 2.1 表: `platform_snapshots`

当前版本使用快照式业务状态表，统一承载平台核心状态。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `snapshot_key` | `VARCHAR(64)` | PK | 状态分区键 |
| `payload` | `LONGTEXT` | NOT NULL | JSON 快照内容 |
| `updated_at` | `VARCHAR(64)` | NOT NULL | 最近更新时间 |

### 2.2 快照键说明

| `snapshot_key` | 内容 |
|------|------|
| `auth` | 用户、密码哈希、会话 token |
| `chat-history` | 聊天历史与会话消息 |
| `evaluation` | 评测题库、系统答案、人工评分 |
| `documents` | 文档元数据、切块信息、向量回退数据 |

### 2.3 设计原因

- 当前平台是单后端实例部署，快照式状态足以覆盖业务需求
- 避免在答辩和演示阶段为多个轻量模块维护大量表结构
- 保留后续拆分为标准化表结构的空间

## 3. Neo4j 设计

### 3.1 主要标签

- `LitchiVariety`
- `Disease`
- `Pest`
- `Pesticide`
- `CultivationTechnique`

### 3.2 主要关系

- `HAS_DISEASE`
- `HAS_PEST`
- `TREATS`
- `PREVENTS`
- `NEEDS_TECHNIQUE`
- `SIMILAR_TO`

### 3.3 典型查询

```cypher
MATCH (d:Disease {name: '炭疽病'})<-[:TREATS]-(p:Pesticide)
RETURN d, p
```

```cypher
MATCH (v:LitchiVariety {name: '桂味'})-[:HAS_DISEASE]->(d:Disease)
RETURN v, d
```

## 4. Milvus 设计

### 4.1 Collection

| 名称 | 说明 |
|------|------|
| `litchi_knowledge` | 文档切块向量索引 |

### 4.2 文档切块字段

| 字段 | 说明 |
|------|------|
| `id` | 切块 ID |
| `title` | 文档标题 |
| `content` | 切块文本 |
| `source` | 来源文件 |
| `page` | 切块页码或段序 |
| `vector` | 向量数据 |

### 4.3 回退策略

如果 Milvus 不可用，后端会使用本地内存中的切块向量执行相似度检索，保证演示链路可用。

## 6. 数据流说明

### 6.1 登录流程

1. 后端校验用户名和密码哈希
2. 创建 token 会话
3. 状态写入 MySQL
4. 同步写入本地 JSON 回退文件

### 6.2 文档上传流程

1. 原文件写入本地文档目录
2. 提取文本并切块
3. 切块写入内存与 Milvus
4. 文档状态写入 MySQL
5. 同步写入本地 JSON 回退文件

### 6.3 问答流程

1. 前端带 token 调用 `/chat`
2. 后端执行图谱增强与文档检索
3. 返回答案、来源、图谱片段
4. 会话历史写入 MySQL 与本地回退文件
