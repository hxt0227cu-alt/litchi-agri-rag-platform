# 数据库设计

## 1. 总体存储架构

平台当前采用“结构化主存储 + 图谱 + 向量索引 + 本地状态回退”的组合方案：

- MySQL：账号、会话、聊天、评测、文档元数据与文档分块、门店协同、满意度反馈
- Neo4j：知识图谱实体与关系
- Milvus：文档分块向量索引
- 本地文件系统：上传原始文档与 JSON 回退状态

当前实现中的关键特点：

- 账号、聊天、评测、文档、协同、满意度反馈已迁移为标准化 MySQL 表。
- 后端会把上述状态同步到本地 JSON 文件，便于离线运行和故障回退。
- 文档原文件不存入 MySQL，而是存储在后端文件目录。

## 3. Neo4j 设计

### 3.1 主要标签

- `LitchiVariety`
- `Disease`
- `Pest`
- `Pesticide`
- `CultivationTechnique`

### 3.2 主要关系

- `HAS_DISEASE`
- `HAS_PEST`
- `TREATS`
- `PREVENTS`
- `NEEDS_TECHNIQUE`
- `SIMILAR_TO`

### 3.3 典型查询

```cypher
MATCH (d:Disease {name: '炭疽病'})<-[:TREATS]-(p:Pesticide)
RETURN d, p
```

```cypher
MATCH (v:LitchiVariety {name: '桂味'})-[:HAS_DISEASE]->(d:Disease)
RETURN v, d
```

## 5. 本地文件设计

### 5.1 上传文档目录

- 默认目录：`data/documents`
- Docker 挂载目录：`/app/data/documents`

### 5.2 回退状态文件

| 文件 | 当前用途 |
| --- | --- |
| `data/auth-state.json` | 用户与会话回退 |
| `data/chat-history.json` | 问答历史回退 |
| `data/evaluation-state.json` | 评测题库与评分回退 |
| `data/document-state.json` | 文档元数据与切块回退 |
| `data/feedback-state.json` | 满意度反馈回退副本 |
| `data/collaboration-state.json` | 门店资料、方案、求助回退副本 |

### 5.3 协同模块本地状态结构

`data/collaboration-state.json` 当前作为回退副本，包含三类记录：

- `profiles`：门店资料
- `plans`：门店方案
- `consultations`：农户求助记录

### 5.4 满意度反馈本地状态结构

`data/feedback-state.json` 当前作为回退副本，以 `records` 数组保存反馈记录，包含用户、角色、模块、评分、备注和创建时间。

## 6. 数据流说明

### 6.1 登录流程

1. 后端校验用户名和密码哈希。
2. 创建 token 会话。
3. 状态写入 MySQL。
4. 同步写入本地 JSON 回退文件。

### 6.2 文档上传流程

1. 原文件写入本地文档目录。
2. 提取文本并切块。
3. 切块写入 MySQL 与 Milvus。
4. 文档状态同步写入本地 JSON 回退文件。

### 6.3 问答流程

1. 前端带 token 调用 `/chat`。
2. 后端执行文档检索和图谱实体召回。
3. 调用 Ollama 生成回答，失败时回退到本地保障回答。
4. 会话历史写入 MySQL 与本地回退文件。

### 6.4 门店协同流程

1. 门店维护 `profiles` 和 `plans`。
2. 农户根据推荐结果提交 `consultations`。
3. 门店更新求助状态。
4. 协同状态写入 MySQL，并同步写入 `data/collaboration-state.json` 回退副本。

### 6.5 满意度反馈流程

1. 用户提交评分和备注。
2. 后端校验评分范围和备注长度。
3. 反馈记录写入 MySQL，并同步写入 `data/feedback-state.json` 回退副本。

## 7. 当前状态总结

- 当前数据库设计已经从旧版快照表迁移为标准化 MySQL 表。
- MySQL 主存储覆盖账号、聊天、评测、文档、协同和满意度反馈六类核心数据。
- 这种设计在答辩和课程验收场景下更利于快速部署和稳定演示。

## 8. 后续可扩展点
