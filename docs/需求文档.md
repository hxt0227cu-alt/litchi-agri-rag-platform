# 需求文档

## 0. 文档说明

- 更新时间：2026-03-25
- 适用范围：当前仓库已实现版本
- 文档目的：将原始立项阶段的需求描述，更新为与当前项目状态一致的“版本需求基线”，用于开发对齐、验收说明和答辩材料引用。

## 1. 项目背景

随着人工智能、大模型、知识图谱和 RAG 技术的发展，将其应用到农业场景具有较强的现实意义。荔枝作为南方重要经济作物，在种植过程中长期存在以下痛点：

- 病虫害识别依赖经验，农户自判断难度大。
- 专业技术知识分散在文档、经验和人工咨询中，获取成本高。
- 门店配药建议与农户问题之间缺少线上协同链路。
- 纯问答系统难以支撑“识别、推荐、跟进、优化”的完整闭环。

基于以上背景，当前项目已从早期“荔枝智能问答 Web 平台”，演进为一个面向农户、农资店主和技术员三类角色的荔枝智能问答与协同诊断平台。

## 2. 项目目标

当前版本的目标如下：

- 构建面向荔枝种植场景的本地可部署智能服务平台。
- 提供病害识别、智能问答、知识图谱、知识文档管理等 AI 能力。
- 建立“农户发起问题 -> 门店承接方案 -> 技术员持续优化”的协同闭环。
- 支持技术员对知识来源、系统状态和评测结果进行统一管理。
- 保留本机运行与 Docker 全栈运行两种形态，并具备降级保障能力。
- 满足课程验收和答辩展示所需的功能闭环、构建验证与性能说明。

## 3. 当前版本定位与边界

### 3.1 系统定位

当前版本定位为：

- 一个面向荔枝种植场景的多角色智能协同平台；
- 一个结合大模型、向量检索、知识图谱和病害识别的农业 Web 系统；
- 一个适合本地部署、答辩演示和课程验收的完整工程项目。

### 3.2 当前业务闭环

当前版本的核心闭环为：

1. 农户在学习课堂、病害识别或智能问答中确认问题。
2. 系统根据病症标签和问题描述推荐门店方案。
3. 农户选择方案后提交求助意向。
4. 门店在收件箱中跟进求助并更新状态。
5. 技术员通过评测中心、知识文档、知识图谱和系统状态页持续优化平台。

### 3.3 当前版本边界

- 当前“用药指南/门店方案”模块提供的是方向建议、风险提醒和沟通辅助，不是精确剂量处方系统。
- 当前系统适合教学、演示和课程验收场景，不应表述为面向生产环境的自动处方平台。
- 对剂量、混配、安全间隔期等高风险问题，系统应提示用户结合标签说明、当地植保要求和专业人员判断。

## 4. 用户角色与核心需求

| 用户角色 | 核心需求 | 当前主要入口 |
| --- | --- | --- |
| 农户 `farmer` | 学习常见病症、拍照识别、智能问答、查看推荐方案、向门店提交求助、反馈满意度 | 农户工作台、学习课堂、病害识别、智能问答、解决方案、我的求助 |
| 农资店主 `shopkeeper` | 维护店铺资料、维护门店方案、承接农户求助、查看高频病症趋势 | 门店工作台、店铺管理、配药方案、待处理求助、高频病症 |
| 技术员 `technician` | 维护知识文档、查看知识图谱、开展评测与人工复核、查看系统状态 | 技术支持台、评测中心、知识文档、研判图谱、系统状态 |

### 5.6 安全与边界要求

| 功能点 | 描述 | 优先级 |
| --- | --- | --- |
| 密码安全存储 | 用户密码必须以哈希加盐方式存储，不允许明文保存 | P0 |
| 会话有效期 | 登录 token 需具备过期时间和服务端会话管理 | P0 |
| 系统配置脱敏 | 展示系统连接信息时应对密码等敏感字段做脱敏 | P1 |

| 用药安全边界 | 系统必须明确“建议性质”，避免宣称输出精确剂量处方 | P0 |

## 6. 非功能需求

### 6.1 性能与稳定性

| 指标 | 目标要求 | 当前验证情况 |
| --- | --- | --- |
| 智能问答平均响应时间 | `< 5 秒` | 2026-03-17 基线测试结果为 `4159.4 ms` |
| 图像识别平均响应时间 | `< 3 秒` | 2026-03-17 基线测试结果为 `76.65 ms` |
| 并发能力 | 支持 `50+` 并发用户 | 2026-03-17 已完成 `50` 并发、`50` 请求压测，成功率 `100%` |
| 系统可用性 | `> 99%` | 2026-03-17 已完成连续 `5` 分钟、`30` 轮巡检，可用率 `100%` |

### 6.2 安全性要求

- 用户密码采用哈希加盐存储。
- 系统采用 token 鉴权和角色权限控制。
- 关键写操作需输出统一审计日志。
- 对系统设置中的敏感连接信息做展示脱敏。
- 对用药建议类页面明确“非精确处方”边界。

### 6.3 兼容性与部署要求

- 支持 Chrome、Firefox、Edge、Safari 等主流浏览器访问。
- 支持移动端页面访问与基础交互。
- 支持 Windows/Linux 本机部署。
- 支持 Docker 全栈一键启动。
- 当前版本已具备相关页面和布局支持，但浏览器与手机实机验收记录仍需线下补测补档。

### 6.4 可维护性与可扩展性

- 系统应采用前后端分离与模块化设计，便于后续扩展功能。
- 病害识别、知识图谱、向量检索和大模型推理应保持服务边界清晰。
- 支持新增荔枝病虫害类型、门店方案类型、知识文档和模型版本。
- 在关键依赖不可用时，应尽量保留演示级和基础可用能力。

## 7. 数据需求

### 7.1 知识图谱数据

当前系统需覆盖以下主要实体方向：

| 实体类型 | 目标覆盖 |
| --- | --- |
| 荔枝品种 | `20+` |
| 病害 | `50+` |
| 虫害 | `30+` |
| 农药/药剂 | `100+` |
| 栽培技术 | `50+` |

### 7.2 文档数据

- 支持上传 `txt`、`md`、`pdf`、`docx` 文档。
- 文档用于知识问答、来源追溯和技术员维护。
- 文档在入库后需完成抽取、切块、索引和状态记录。
- 当前仓库包含演示文档与本地文档存储目录，用于新环境初始化和答辩演示。

### 7.3 图像与模型数据

- 支持果园原始图片、标注图片和 YOLO 训练集管理。
- 识别服务优先加载 `models/yolov8-litchi.pt` 权重。
- 当正式权重不可用时，应保留数据集特征匹配或规则兜底模式。

### 7.4 评测数据

当前评测中心按以下类型组织题库：

| 问题类型 | 目标规模 |
| --- | --- |
| 品种介绍 | `15` 左右 |
| 种植技术 | `20` 左右 |
| 病害识别 | `25` 左右 |
| 虫害防治 | `20` 左右 |
| 农药使用 | `10` 左右 |
| 综合问题 | `10` 左右 |
| 总计 | `100` 题左右 |

## 8. 当前版本验收基线

当前版本在课程验收和答辩层面的最低完成标准如下：

- 前端测试、前端构建、后端测试、后端打包可通过。
- 账号、问答、图谱、文档、识别、学习课堂、门店方案协同、满意度反馈形成闭环。
- 技术员能够完成知识维护、评测复核和系统状态查看。
- 门店能够维护方案并处理农户求助。
- 农户能够从识别或问答进入推荐方案，再提交求助并查看状态。
- 性能、并发和稳定性有明确验证记录。

当前仍需补充的线下验收项：

- 主流浏览器实机兼容性验证；
- Android 与 iPhone 关键页面实机验证。

## 9. 约束条件

- 项目周期按课程与毕业设计节奏推进，整体属于学生项目范围。
- 部署环境以本地服务器或个人电脑为主。
- 预算有限，优先采用本地模型、本地服务和可离线运行方案。
- 当前版本强调“完整演示与工程闭环”，不追求生产级处方决策深度。

## 10. 一句话总结

当前版本的需求已经从“单一荔枝智能问答平台”，更新为“面向农户、门店和技术员三类角色的荔枝智能问答与协同诊断平台”，并以本地部署、可追溯问答、病害识别、门店协同和技术员持续优化为核心范围。
