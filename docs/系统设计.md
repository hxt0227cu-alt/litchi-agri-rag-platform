# 系统设计文档

## 1. 系统定位

当前系统定位为“荔枝智能问答与协同诊断平台”。平台面向荔枝种植、门店服务和农技支持三类场景，提供统一账号体系、病害识别、智能问答、知识图谱、知识文档、评测中心、门店方案协同和系统运维入口。当前版本支持本机运行和 Docker 全栈运行两种形态，并保留多处降级保障路径。

## 2. 总体架构

平台采用前后端分离架构，并将大模型推理、知识图谱、向量检索和病害识别拆分为独立能力模块。

```text
浏览器前端 Vue 3
    ↓ HTTP / JSON
Spring Boot 后端 API
    ├─ 认证与角色权限
    ├─ 农户工作流（学习、识别、问答、推荐、求助）
    ├─ 门店协同（资料、方案、收件箱、趋势）
    ├─ 技术员工作流（评测、知识文档、图谱、系统状态）
    ├─ 文档解析与向量检索
    ├─ 知识图谱查询
    ├─ 病害识别代理
    └─ 系统初始化与健康检查

后端依赖的外部服务
    ├─ MySQL 8：账号、会话、聊天、评测、文档主存储
    ├─ Neo4j 5：知识图谱
    ├─ Milvus 2：文档向量索引
    ├─ Ollama：大模型推理
    └─ diagnosis-service：病害识别 HTTP 服务
```

## 4. 核心模块

### 4.1 认证与权限

- 提供注册、登录、登出、当前用户信息接口。
- 当前内置三类角色：`farmer`、`technician`、`shopkeeper`。
- 权限控制通过 `@AuthRequired` 和 `@RoleAllowed` 在后端统一生效，前端菜单和路由同步限制。
- 当前前端的默认首页分别为：
  - 农户：`/farmer/workbench`
  - 门店：`/shop/workbench`
  - 技术员：`/technician/workbench`

### 4.2 农户工作流

- 农户侧以“学习课堂 -> 病害识别/智能问答 -> 解决方案推荐 -> 提交求助 -> 我的求助 -> 满意度反馈”为主链路。
- 病害识别页支持样图选择和本地图片上传。
- 智能问答页支持会话管理、来源卡片、图谱命中、语音输入和回答朗读。
- 解决方案页会按病症标签、方案质量、门店响应信号和评分综合排序推荐门店方案。
- 农户可基于选中的方案直接提交求助意向，并在“我的求助”中查看状态变化。

### 4.3 门店协同模块

- 门店侧以“工作台 -> 店铺资料 -> 方案库 -> 待处理求助 -> 高频病症趋势”为主。
- 店铺资料模块维护门店名称、联系人、联系方式、服务区域、擅长方向和评分。
- 方案库模块维护门店自己的结构化方案，包括病症标签、阶段标签、摘要、产品、使用提示、风险提醒和库存状态。
- 待处理求助收件箱支持把求助状态更新为 `pending`、`contacted`、`completed`。
- 趋势看板按农户真实求助记录聚合病症热度，不混入浏览点击数据。

### 4.4 技术员工作流

- 技术员工作台集中展示服务健康、文档索引、低分评测和协同概况。
- 评测中心支持题库分页、系统答案提交、自动评分、BLEU、人工评分和统计汇总。
- 知识文档页由技术员统一维护文档来源。
- 研判图谱页用于查看图谱结构、实体详情和关系信息。
- 系统状态页用于查看依赖服务健康、运行参数、平台概览和初始化入口。

### 4.5 智能问答与会话历史

- 问答接口支持向量检索增强与知识图谱增强开关。
- 问答响应包含回答内容、文档来源片段和图谱命中实体。
- 问答结果会按用户维度写入会话历史，支持会话列表和分页回放。
- 对热点问题保留短时缓存，并在模型不可用时使用本地保障回答。

### 4.6 文档管理与检索

- 支持上传 `txt`、`md`、`pdf`、`docx`。
- 文档会进行文本抽取、切块、向量化，并同步到 MySQL、本地状态文件和 Milvus。
- PDF 解析使用 PDFBox，DOCX 解析使用 Apache POI。
- 当 Milvus 不可用时，仍可回退到本地分块检索，保证问答链路可用。

### 4.7 知识图谱

- 图谱实体包括品种、病害、虫害、药剂、栽培技术等。
- 图谱服务支持可视化、关键词搜索、实体详情查询。
- 启动初始化时会把平台样例节点和关系合并到 Neo4j。
- 当 Neo4j 不可用时，会退回到内置演示图谱数据。

### 4.8 病害识别

- 前端提供识别工作台，支持样图和真实图片上传。
- 后端将图片转发给独立的 `diagnosis-service`。
- 识别服务优先使用 `models/yolov8-litchi.pt` 对应的 YOLO 模型。
- 当正式模型或依赖不可用时，会降级到数据集特征匹配或规则兜底模式。

### 4.9 满意度与安全边界

- 所有已登录用户都可通过接口提交满意度反馈，前端当前主要向农户和技术员提供入口。
- 技术员可查看满意度统计和最近反馈。
- 平台已明确“门店方案/建议展示不等于精确处方”的安全边界。
- 后端已增加统一审计日志，对关键写操作记录处理器、路径、状态码、耗时和用户信息。

### 4.10 系统初始化与运维

- 提供 `/api/health`、`/api/system/overview`、`/api/system/settings`、`/api/system/init`、`/api/system/demo/bootstrap`。
- Docker 模式默认开启自动启动引导：
  - 自动准备样例文档
  - 自动初始化知识图谱
  - 自动初始化向量集合并同步分块
- 新环境启动后即可直接进行问答、图谱、识别和协同演示。

## 5. 数据存储设计

### 5.1 MySQL 主业务表

当前已经标准化落表的主业务数据包括：

- `platform_users`
- `platform_sessions`
- `platform_chat_messages`
- `platform_evaluations`
- `platform_documents`
- `platform_document_chunks`

### 5.2 本地状态文件

当前以下模块仍保留本地状态文件：

- `data/auth-state.json`
- `data/chat-history.json`
- `data/evaluation-state.json`
- `data/document-state.json`
- `data/feedback-state.json`
- `data/collaboration-state.json`

其中账号、聊天、评测、文档、协同和满意度反馈在启用 MySQL 时均具备结构化主存储；本地状态文件继续承担离线回退和故障副本职责。

### 5.3 其他存储

- Neo4j：保存图谱实体与关系。
- Milvus：保存文档分块向量索引。
- 后端本地目录：保存上传原文件、状态回退文件和演示数据。

## 8. 部署形态

### 8.1 本机开发

- 本机启动 MySQL、Neo4j、Milvus、Ollama、识别服务
- 本机运行 Spring Boot 和 Vue 前端
- 适合本地调试接口、页面和识别服务

### 8.2 Docker 全栈

`docker-compose.yml` 当前编排的服务包括：

- `mysql`
- `neo4j`
- `etcd`
- `minio`
- `milvus`
- `ollama`
- `ollama-model-init`
- `diagnosis-service`
- `backend`
- `frontend`

## 9. 当前设计特点

- 平台已经从单一问答系统扩展为三角色协同平台。
- 主业务数据已从快照式存储迁移到标准化 MySQL 表，仍保留本地回退能力。
- 门店协同和满意度反馈当前仍保留轻量本地状态文件，以降低演示复杂度。
- Docker 启动后具备自动引导能力，不再依赖手动准备演示样例。
- 文档检索、图谱检索、病害识别和大模型问答都保留了降级保障路径。
